## 1. 项目真正解决什么问题

### 1.1 产品定位

**[事实]** 这是一个嵌入 DSH Web GUI／桌面应用侧边栏底部的只读信息插件。它把四类分散信息集中到一个卡片中：

1. 当前所选模型通常由哪个余额付费：DSH 账号余额，或 API Key 对应的 DeepSeek 开放平台余额。
2. 当前模型在现行峰／谷时段的输入、缓存命中输入、输出单价。
3. 当前是高峰还是空闲，以及距离下次切换的倒计时。
4. 中文界面下，今天是否是中国法定节假日或调休日。

证据：`README.zh-CN.md:23-30`、`package.json:2-4`、`client.js:1-21`。

**[事实]** 代码不统计 token 用量，不计算一次会话消费，不生成账单，不充值、不扣费，也不调用支付能力。所有网络访问都是读取，没有业务回写；其中只有开放平台余额请求携带 API Key。

**[推断]** 产品的核心价值是“做模型／提供商选择时的费用可见性”，而不是账务核算。卡片上的金额和价格是决策参考，不能被解释为插件自行算出的应付账单。

### 1.2 用户痛点

**[推断]** 它主要缓解四个痛点：

- 用户不容易判断当前会话到底消耗 DSH 账号额度还是自己的开放平台额度。
- 官方价格随模型、token 类别和峰谷变化，手动查表成本高。
- 高峰窗口按北京时间和法定节假日计算，与用户本地时区不一致。
- 余额、模型选择、价目和节假日分散在宿主与多个上游中。

## 3. 用户、宿主与项目的关系

| 角色 | 提供／承担 | 从项目获得／向项目提供 |
| --- | --- | --- |
| 最终用户 | 选择模型和提供商、登录 DSH、配置 API Key | 获得余额、价格、峰谷和节日信息 |
| DSH 宿主 | Client 插槽、React、语言、计时器、账号、模型目录、当前会话、事件；Host 凭据、日志、可选 Web Server | 承载插件生命周期和 UI；不依赖插件完成核心计费 |
| 插件 Host | 跨域读取、凭据保护、上游解析、内存状态、HTTP 数据路由 | 向 Client 提供已解析数据，不暴露 API Key |
| 插件 Client | DSH 数据读取、领域规则、刷新协调、格式化与渲染 | 把宿主和 Host 数据组合成卡片 |
| 外部上游 | DeepSeek 价目与余额、iCloud 日历 | 是数据权威来源，不接收插件业务回写 |

**[事实]** Host 与 Client 的生效生命周期不同：Host 改动需完整重启，Client 改动需页面刷新；manifest／bundle patch 还需重新添加 bundle。证据：`AGENTS.md:14-27`。

**[推断]** 项目不是独立应用，而是宿主能力的组合器。重建时真正需要优先稳定的是宿主适配边界和数据契约，而不只是 React 组件结构。

## 4. 核心业务流程

### 4.1 启动数据准备

**[事实]**

1. Host 建立 `loading/pending` 状态。
2. 并行加载 CNY 价目、USD 价目、iCloud 日历和开放平台余额。
3. 三个 HTTP 文档请求各有 8 秒超时；失败按来源记录 warning。
4. 价目和日历只在启动时读取；余额有独立的 30 秒刷新。
5. Web Server 出现后注册路由；路由始终回答内存状态，不在请求路径等待上游。
6. Client 请求并二次校验路由数据；不可用的来源使用内置副本。

证据：`index.js:45-51,99-142,218-262`；`client.js:760-817,1585-1725`。

### 4.2 当前模型与提供商解析

**[事实]** 选择优先级为：当前可见会话选择 > 模型目录默认值 > 加载／失败占位。模型目录另提供模型和提供商显示名。可选会话服务缺失时每秒重试，最多 15 次。证据：`client.js:922-940,1538-1582,1728-1844`。

### 4.3 余额归属与降级

**[事实]** 正常路径下：

- 只有 `deepseek-official` 默认头行开放平台余额。
- `deepseek-account`、`deepseek`、其他或未知提供商头行 DSH 账号余额。
- 非开放平台提供商且 DSH 明确登出时，API 余额可作为最佳可用金额。
- 开放平台余额缺失和读取失败分别显示通知，不伪装成金额。

证据：`client.js:44-62,990-1106`。

**[推断]** “当前模型的付款余额”是正常路径语义；在旧 Host、路由失败、账号登出等降级路径中，实际语义是“按既定优先级显示最佳可用余额”。这两种语义需要在 2.0 中被明确区分。

### 4.4 计费时段与价格

**[事实]**

- 北京时间周一到周五 `[09:00,12:00)`、`[14:00,18:00)` 为高峰。
- 周末和法定休假日全天空闲。
- `makeup` 不直接参与计费；周末调休因周末规则而空闲。
- 下一次切换通过扫描未来最多 400 天的窗口边界得出。
- 价格按模型 id、显示名和静态别名查找，再按当前峰／谷选择三类单价。
- 中文 locale 使用 CNY 表，其他 locale 使用 USD 表；不做汇率换算。

证据：`client.js:235-278,370-410,504-526,1142-1149`。

### 4.5 持续刷新与即时变更

| 触发 | 当前动作 | 证据 |
| --- | --- | --- |
| 每秒 | 展开时更新当前时间和倒计时 | `client.js:713-716` |
| Client 每 30 秒 | 展开时读取账号、模型目录和 Host 路由 | `client.js:819-853` |
| Host 每 30 秒 | 重新解析 Key 并读取开放平台余额 | `index.js:238-251` |
| 会话选择变化 | 更新选择、立即读账号；提供商变化时请求 API 余额刷新 | `client.js:723-745` |
| 提供商／设置／凭据事件 | 请求 `?balance=refresh` | `client.js:747-758,1858-1879` |
| 显式刷新 | Host 后台读，路由先答旧状态；Client 最多两次、每秒跟进 | `index.js:196-215`；`client.js:789-797` |

## 5. 数据从哪里来，如何处理，流向哪里

| 数据 | 权威来源 | 处理 | 最终去向 |
| --- | --- | --- | --- |
| DSH 充值／赠金钱包 | `ctx.remote.account.getBalance()` | 按币种筛选；十进制字符串用 BigInt 求和；汇总后向零截断 | 头行金额、余额气泡 |
| 模型与提供商 | 会话 store + `modelCatalog()` | 会话覆盖默认；id 规范化、别名解析、官方 provider 判定 | 模型行、provider 行、价格和余额选择 |
| API Key | `credentials.resolve()`，环境变量回退 | 仅 Host 使用，转为 Bearer header | DeepSeek 余额请求；不进入路由 DTO |
| 开放平台余额 | `api.deepseek.com/user/balance` | 只接受 CNY/USD 与非负十进制；优先 CNY | Host 内存 → JSON → 头行或气泡 |
| CNY/USD 价目 | 两个 DeepSeek 官方文档页 | HTML 表格解析；只保留峰谷三类价格完整的模型 | 中文／非中文价格区与模型气泡 |
| 节假日／调休 | iCloud `cn_zh.ics` | ICS 折行、休／班标记、排他 DTEND、休优先 | 所有语言的计费；中文标签 |
| 内置价目 | `PRICE_SNAPSHOT` | 2026-10-26 快照，两个模型和两个别名 | 对应币种实时表不可用时整表回退 |
| 内置日历 | `HOLIDAY_RANGES`、`MAKEUP_DAYS` | 2025–2026 年固定副本 | Host 日历不可用时整表回退 |

**[事实]** 没有业务数据库、插件自有持久化、分析上报或业务回写。账号请求会携带 DSH 版本、locale 和本地时区偏移元数据。证据：`client.js:1496-1523`。

**[事实]** Host 路由的 `sources`、顶层 `at`、日历 `years`、余额 `available/at` 当前不被 Client 的展示决策使用。证据：`client.js:1692-1725`。

## 6. 外部依赖与宿主能力

### 6.1 已证实的外部依赖

**[事实]**

- DeepSeek 中文和英文价目页、开放平台余额端点：`parse.js:15-23`。
- Apple iCloud 中国大陆日历：`parse.js:24-25`。
- 宿主提供的 React；Client 唯一模块导入是 `require('react')`：`client.js:23-33`。
- Host 标准能力：`fetch`、`AbortSignal.timeout`、`Buffer`、`process.env`、定时器。
- Client 标准能力：浏览器 `fetch`、`Intl.NumberFormat`、`BigInt`、DOM、可选 `ResizeObserver`／`MutationObserver`。
- CSS 使用 `light-dark()` 和 `color-mix()`：`client.js:592-650`。

### 6.2 宿主服务边界

**[事实]** Client 必需注入：`slots`、`locale`、`timer`、`remote`、`remote.account`、`remote.session`；可选获取 `uiSession` 和 `modelDirectories`。Host 可选使用 `credentials`、`logger`、`webServer`。证据：`client.js:1492-1495,1744-1766`；`index.js:60-65,152-164,253-262`。

**[推断]** 当前仓库不能证明 Host 能读取与浏览器一致的账号、模型目录和“当前可见会话”选择。因此任何把全部聚合迁往 Host 的重建方案都有前置能力验证，不应当作现成能力。

## 7. 已实现功能清单

**[事实]** 当前代码已经实现：

- 两类余额读取、付款方感知头行、充值／赠金分解。
- 同币种精确合计、跨币种不换算、正数不足一分的专门显示。
- 当前模型三类峰／谷单价、模型别名、官方 provider 白名单。
- 北京时间峰谷判断、下一切换倒计时、法定节假日排除。
- 中文节日横条、调休 chip、同日“休”覆盖“班”。
- 中英词典、CNY/USD 表选择、非中文余额 ISO 前缀。
- 明暗主题、自绘气泡、键盘焦点与 Escape、折叠恢复。
- 启动快照、每源回退、30 秒余额刷新、提供商／凭据事件触发刷新。
- 无 Web Server 时 Host 仍可激活；路由坏数据在 Client 再校验。
- 离线解析器、Host 和 Client 测试；本次复跑为 **1004 PASS / 0 FAIL**。

## 9. 隐含语义与待确认问题

### 9.1 已知语义

- **[事实]** 价格币种由界面语言决定，不由钱包币种或账号地区决定：`client.js:235-265`。
- **[事实]** 实时表与内置表按来源整表替换，不按模型或年份合并：`client.js:906-915`。
- **[事实]** 内置日历未覆盖的年份被当作“无已知节假日”，仍按工作日规则：`client.js:280-304,376-386`。
- **[事实]** `is_available` 被解析但 Client 丢弃，不阻止金额显示：`parse.js:93-100`；`client.js:1692-1705`。
- **[事实]** 开放平台总额直接采用 `total_balance`，不验证是否等于充值加赠金：`parse.js:93-100`。
- **[事实]** 空闲价直接读上游，不用 `peak / 2` 推导：`parse.js:298-315`；`client.js:1142-1149`。
- **[事实]** 价目 `asOf` 是 Host 抓取时的北京日期，不必然是价格生效日期：`index.js:120-125`。

### 9.2 文档和代码缺口

- **[事实]** README 的“实时单价”实际指按当前时刻选择启动快照中的峰／谷价，不是价目持续实时更新：`README.zh-CN.md:8,88-95`。
- **[事实]** README 只写无 Web Server 时价目和日历回退；实际上 Client 也收不到 Host 已读取的开放平台余额：`README.zh-CN.md:90-95`；`client.js:1082-1087`。
- **[事实]** Host 注释称失败时保留最后成功余额，代码却立即改写为 `failed`：`index.js:166-171,189-193`。
- **[事实]** 调休气泡写“调休日按周末处理，全天不计高峰”，算法实际只按周末和休假日判断；该文案依赖当前调休日均在周末的数据事实：`client.js:123,376-386`。

### 9.3 需要负责人确认的产品问题

- **[建议]** 日历缺失或覆盖年份之外，应继续按工作日计费，还是显示“计费日历未知”并避免给出确定峰谷？
- **[建议]** API 余额暂时失败时，应保留并标记最后成功值，还是像当前代码一样撤下金额？
- **[建议]** 路由暂时失败与“旧 Host 没有余额能力”是否必须区分，以免显示错误付款方余额？
- **[建议]** “界面语言决定价目币种”是否仍是 2.0 产品策略，还是允许用户独立选择？
- **[建议]** 调休的普遍规则与当前数据特例如需长期共存，应由领域规则还是文案承担解释？

## 10. 重建范围建议

**[建议]** 默认保留“余额 + 当前模型价目 + 峰谷倒计时 + 节假日”的只读卡片定位，优先修正数据可信度和状态语义；不要在本次重建中顺带加入用量统计、账单、支付或通用多提供商平台，除非负责人另行扩大产品范围。
