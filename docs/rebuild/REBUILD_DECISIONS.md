# dsh-billing-card 2.0：重建决策清单

> 目的：列出必须由项目负责人确认的决策，不把分析者的推荐当作已批准结论  
> 状态：全部待确认；本阶段未实施任何一项  
> 标记：**[事实]** 当前基线；**[推断]** 影响判断；**[建议]** 推荐默认值

## 1. 建议的决策顺序

1. **先定产品与正确性语义**：保留什么、付款方、快照、日历和失败时显示什么。
2. **再定兼容与宿主边界**：支持哪些 DSH、哪些新旧半部组合、是否改变路由和适配方式。
3. **再定工程方案**：是否采用推荐的方案 A、TypeScript、构建、依赖和测试策略。
4. **最后定迁移、发布和 Agent 治理**：版本、灰度、回滚、旧 API 下线、Skills 和文档所有权。

**[推断]** 如果先选框架再决定降级语义，容易把当前“路由失败就显示另一账户余额”等历史行为误固化进新架构。

## 5. 配置迁移决策

**[事实]** 当前没有插件自有的持久化用户配置 schema。实际配置主要是 DSH Models 页保存的 `DEEPSEEK_API_KEY`、启动环境同名变量、bundle 稳定 id、manifest 和 npm 安装状态。

| ID | 必须确认的问题 | 推荐默认值 |
| --- | --- | --- |
| D-27 | 旧 `DEEPSEEK_API_KEY` 是否原样复用？ | **[建议] 复用 DSH 凭据 store，不复制或迁移密钥到插件自有存储；环境变量仅作明确回退。** |
| D-28 | 若新增刷新、币种、provider 或 UI 设置，配置存哪里、如何迁移？ | **[建议] 优先无配置默认值；确需设置时使用版本化 schema、默认值和向前迁移，不读取不存在的历史配置。** |
| D-29 | bundle id 和安装状态是否保持？ | **[建议] 默认保持 `dsh-billing-card` 稳定 id，避免升级重复挂载或丢失禁用／覆盖状态；若改宿主机制需专门迁移。** |

**[推断]** “2.0 允许不兼容”不等于必须制造配置迁移；当前最安全的做法是让密钥和安装状态不被重建触碰。

## 10. 给项目负责人的摘要

### 主要问题

**[事实]** 当前 1004 条离线断言全绿，但仍存在：异常模型 id／坏钱包可崩溃、无效钱包可少算、非法币种可误标 CNY、凭据可阻塞启动、Host／Client 可旧响应覆盖新状态、部分 loading 被提前 ready、路由失败可显示错误付款方余额。Client 1912 行集中所有职责，DTO 无版本，真实浏览器与 DSH 覆盖不足。

### 推荐方案

**[建议]** 采用方案 A：契约优先的 TypeScript 分层双端模块化单体。保留 Host 管跨域和 Key、Client 管可见会话和倒计时；共享纯 Domain，增加 Contracts 和 Application 状态机，UI 只消费 ViewModel。轻量构建产出两个自包含入口，不新增运行时 npm 依赖。B 需要未证实的 Host 能力，C 超出当前规模。

### 最关键的确认事项

1. 保留哪些核心功能，2.0 是否严格保持只读卡片范围。
2. 日历过旧、余额失败、付款方不可用和多币种时的正确显示语义。
3. v1/v2 API 与新旧 Host/Client 的支持矩阵，旧路径何时下线。
4. 是否批准 TypeScript、轻量构建和开发依赖，同时保持 React 为唯一 Client 外部运行时依赖。
5. 支持哪些 DSH／WebView，是否要求真实多版本 E2E。
